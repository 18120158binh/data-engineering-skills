# Postgres

Operational tables written by apps and stream jobs, and read by apps, jobs through CDC, and analysts.

## Keys

- **Facts** (things that happened): the primary key is the natural identity of the fact, for example `(order_id, line_number)` for an order line, or `(customer_id, campaign_id, step_id)` for a customer completing a campaign step. No surrogate id. The key is what a replay deduplicates on.
- **Entities created by people or apps**: `id uuid PRIMARY KEY` generated by the server, plus `UNIQUE` on the natural key.
  - When a system supplies the natural key, for example `(oidc_issuer, oidc_subject)` for a staff account, create with `INSERT ... ON CONFLICT (<natural key>) DO UPDATE`, so a retry converges and the id of a new row is never used when the entity already exists.
  - When a person chooses it, for example a template name, create with `INSERT ... ON CONFLICT (<natural key>) DO NOTHING RETURNING id`. No row back means a conflict: report it to the person (and offer restore when the existing row is soft-deleted). An upsert here would let one person overwrite another's row.
- **Content-addressed definitions**: when the definition is its identity, the id is a hash of its canonical JSON, for example a short type prefix plus 16 hex digits of a SHA-256.
- Choose the identifier that stays the same. Email is for display and is not unique; it is never the key of an account.

## Writes

- One writer per row, routed by the row's owner (the stream is keyed by the owner before the sink). If two subtasks of one job can write the same row, they deadlock.
- Idempotent writes only:
  - upsert: `INSERT ... ON CONFLICT (<natural key>) DO UPDATE SET ...`
  - write once: `INSERT ... ON CONFLICT DO NOTHING`, or `INSERT ... SELECT ... WHERE NOT EXISTS (...)`
- Replace in place only behind a version guard:
  ```sql
  INSERT INTO user_metrics (...) VALUES (...)
  ON CONFLICT (customer_id, metric_id) DO UPDATE SET ..., last_behavior_version = EXCLUDED.last_behavior_version
  WHERE user_metrics.last_behavior_version < EXCLUDED.last_behavior_version;
  ```
  The producer carries the version. After the producer loses its state, it resumes from `max(version)` in the table.
- A guarded counter on the owner row replaces a whole table in some cases. For example, `session_epoch` on the user row revokes sessions with `UPDATE ... SET session_epoch = session_epoch + 1 WHERE id = $1 AND session_epoch <= $2`, so a stale sign-out cannot end a newer session.
- No shared counter rows. Totals across owners come from a view over the owners' rows, backed by an index that serves the view. Materialize only when `EXPLAIN (ANALYZE, BUFFERS)` shows the view is too slow.
- A Postgres copy of live stream state is a lagging projection. The stream job reads it only when its own state is missing, never on every event.

## Columns and types

- Use the newest type the Postgres version supports, then check it fits: `timestamptz` for points in time, `uuid` for UUIDs (consider `uuidv7()` where the version has it and insert order matters), `bigint` for counts and durations in milliseconds (`retention_ms`).
- When a stream job's contract fixes event time as epoch milliseconds, store it as `bigint` and name it so (`event_timestamp` in ms). Write time is `timestamptz DEFAULT now()`, filled by the database.
- Typed columns for everything that is filtered, joined, or constrained. `jsonb` only for the opaque remainder, such as a rule document a job parses whole.
- `NOT NULL` when every writer must set the value. NULL means unknown.
- CHECK every closed set and every positivity rule: `CHECK (value_type IN ('NUMBER','STRING','BOOLEAN','PRESENCE'))`, `CHECK (retention_ms > 0)`.
- Parallel arrays in one row get CHECKs that keep their lengths equal.

## Relations and deletes

- Definitions and their dependents: `FOREIGN KEY ... ON DELETE CASCADE`, so deleting a definition removes what was derived from it.
- No foreign keys from streamed fact tables to definitions. Facts are written by jobs at high rate, and a fact must not fail because a definition changed.
- Soft delete user-facing entities and projections with `deleted_at timestamptz`. Keep the natural key `UNIQUE` over all rows, deleted or not, so a new row with the same key fails and the caller restores the old one. Every read of these tables filters `deleted_at IS NULL`.
- Hard delete definitions that stream jobs read through CDC, so the job receives a delete.
- Facts are removed only by a retention job.

## CDC sources

- One row carries everything its consumer needs. A consumer that must join several CDC tables cannot rely on the order between them.
- When one logical change writes many rows, put the size of the change on every row (`item_count` on every row of a published definition), so the consumer applies the change only when all rows have arrived.
- Version published definitions with a global sequence (`nextval`), stamped on every row of the definition and carried on everything decided against it. A per-entity counter restarts when the entity is deleted and created again.
- Each CDC-read table gets a publication, and every publication includes the heartbeat table, so an idle slot still advances.
- A CDC snapshot replays existing rows as inserts. Consumers of a fact table must deduplicate across all history.
- Do not put CDC on a table written once per event. The slot cost is too high.

## Tenancy

Decide before data exists. Either one deployment per tenant, or `tenant_id` in every primary key, every unique key, and every index. Adding it later means a migration of every table and a re-keying of all stream state.
